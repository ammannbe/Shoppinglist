# AGENTS.md

Shoppinglist: offline-first PWA for shared shopping lists. One Laravel app serves the UI and the sync API.

## Stack

- Laravel 13, PHP 8.4, MariaDB 10.11, DDEV (`shoppinglist.ddev.site`). Run PHP/Composer/Artisan/npm via `ddev`.
- Auth: Fortify (session cookie, Blade views in `resources/views/auth`), email verification required for syncing. Passkeys via Fortify + `laravel/passkeys` (client `@laravel/passkeys` in `resources/js/auth.js`); managing them requires a password (or passkey) confirmation. Account page `/account` (password change, passkeys) is server rendered and needs a connection.
- Frontend: Blade + Alpine.js + Tailwind 4 (Vite). No SPA framework, no Livewire (must work offline).
- Client database: RxDB (Dexie/IndexedDB storage) with HTTP replication.
- Hosting target: shared hosting with KeyHelp (PHP-FPM + cron, no long running processes, no websockets). Cron every minute: `schedule:run` and `queue:work --max-time=50` (like RecipeManager).

## Optional OpenID Connect login (SSO)

- Off by default; any OIDC provider works (Laravel Socialite + `kovah/laravel-socialite-oidc`, JWT signature verified). Settings in `config/login.php` (`AUTH_LOCAL_*`, `AUTH_OIDC_*`) and `config/services.php` (`oidc`: issuer, client id/secret); same structure as RecipeManager and Chorelist. `App\Auth\OidcProvider` additionally checks `iss`, `aud`/`azp` and `exp` (`OidcClaims`).
- Routes `/auth/oidc/redirect`, `/auth/oidc/callback` (`OidcController`, redirect URI for the provider: `<APP_URL>/auth/oidc/callback`), unlink `DELETE /account/oidc`. Matching in `App\Auth\OidcLogin`: by `users.oidc_sub`, otherwise by email only if the provider marks it as verified. Linking an unverified account verifies it and removes its password, passkeys and sessions (somebody else may have registered or been invited with the address; `AuthenticateSession` skips users without password). Unknown users get a verified account without password (`AUTH_OIDC_REGISTRATION`); `AUTH_OIDC_REQUIRED_GROUP` checks the `groups` claim. The login stays remembered like the password login.
- `AUTH_LOCAL_ENABLED=false` (`RestrictLocalLogin` middleware): the login page shows only the OIDC button (`/login?local=1` shows the form), password logins only for `AUTH_LOCAL_EMERGENCY_EMAILS`, passkey logins are off. `AUTH_LOCAL_REGISTRATION=false` removes Fortify's registration. Password reset stays, so users without password can set one (needed for changing the password and managing passkeys).
- Account page: link/unlink at the top (unlink only with a password, otherwise the account is lost).
- Button label `App\Auth\OidcLabel::get()`: `AUTH_OIDC_LABEL`, otherwise the `appName` (Pocket ID's `APP_NAME`) from the public `<issuer>/api/application-configuration` (cached a day, a failure an hour), otherwise "SSO". Login and registration show the OIDC button first (registration only with `AUTH_OIDC_REGISTRATION`); `AUTH_OIDC_SIGNUP_URL` (e.g. the AccountManager's `/register`) adds "No … account yet?" below it and below "Link …" (`<x-oidc-signup>`). Users switch to SSO voluntarily: linking keeps the local account and its data.
- Local test: Pocket ID runs in the RecipeManager DDEV project (`https://recipemanager.ddev.site:14111`, see its `AGENTS.md`), reached at `AUTH_OIDC_ISSUER=http://ddev-RecipeManager-pocket-id:1411` through the shared `ddev_default` network. Put the `AUTH_OIDC_*` values into the git-ignored `.ddev/config.local.yaml` (`web_environment`). Tests mock Socialite (`tests/Feature/OidcLoginTest.php`).

## Sync architecture

- The UI reads and writes only the local RxDB database; replication runs in the background (`resources/js/db`).
- Server side: `app/Sync/*Resource.php` implement pull (checkpoint `updated_at` + id) and push (conflict detection) per collection, routes `GET /sync/{collection}/pull`, `POST /sync/{collection}/push`.
- IDs are UUIDs generated on the client. Timestamps have millisecond precision (`Syncable` trait).
- Conflicts: every local change increases `version` (RxDB `preSave` hook); the server accepts a push only if `assumedMasterState.version` equals its version and keeps the client's version. Otherwise it returns its document and the server state wins.
- Lists are pulled via memberships (`shopping_list_user`), so revoked access and deleted lists arrive as deleted documents. Any list change has to call `touchForMembers()`; adding a member also touches the items.
- Items of a list unknown to the server return 409, the client retries (list created offline, not pushed yet).
- Sharing/leaving lists needs a connection (`MemberController`). Unknown emails get an account and a password-reset invitation.
- Products, units and shops (`CatalogResource`): own entries per user, public ones (no owner) are read only. Shops (`stores`: name + optional code, max. 10 chars, case kept, `icon`, `countries`): standard shops from `database/data/standard-stores.php`, synced by `shoppinglist:standard-stores` (`--dry-run`; adds/updates, removes unlisted ones, deletes own shops with a standard shop's name or code and retags their owner's items; when the list changes, add a migration that calls it again). Only Migros M, Coop C, Aldi A, Lidl L, Denner D have codes (week planner). Icons: standard shops name a file in `resources/images/shops` (SVG if the shop's mark exists as one, else a small PNG; built and precached by Vite, `resources/js/stores.js`), own shops may have a small image as data URL in the document (max. 64 px, raster only, `StoreResource::ICON_PATTERN`); the badge (`<x-store-badge>`) shows the icon, otherwise the tag. The shop choice only offers standard shops of the user's country (`preferences.country`: CH/DE/AT, set from the device's time zone/language without a location request, existing users CH) and sorts by usage, recent items weighing more (`storeUsage`). Items keep their shops as tags in `items.stores` (JSON list: the code, or the name of a shop without code; copied like `image`, so members of shared lists see them), the badge shows the shop name as tooltip. Names and codes must not collide (both are tags). The edit dialog picks shops as chips (`suggestField` source `store`), an unknown typed one becomes an own shop without code; changing an own shop's tag updates the items. Own shops are managed in `#/stores`; standard shops can be hidden from the shop choice per user (`preferences.hidden_stores`, tags; older entries are codes, which are the tags). A shop picker before the quick entry (`newItemStore`, native select on top of the badge, most used first) sets the shop of new items until changed. Lists can be filtered by shop on the device (`shoppinglist.store-filter`; items without shop stay visible, dragging while filtered moves next to the target row). Pushes from older clients with `store` (one code) and without `recipes` keep working (`ItemResource::attributes`).
- Standard products: public products from `database/data/standard-products.csv` (name, category for review only), synced by `shoppinglist:standard-products` (`--dry-run`): adds missing, removes unlisted ones and deletes own duplicates without image. Run by a migration; when the list changes, add a new migration that calls it again. An own product with the name of a standard product only carries the user's photo: the products view shows the standard product with it, removing the photo deletes the own copy.
- `items.recipes`: recipes the item was planned for (`[{name, url, key}]`, `resources/js/recipe-links.js`). `key` = id of the saved recipe (`planned_recipes`): the name in the row (a link below the row button, not inside it, also on done rows) and in the edit dialog opens `#/recipes/<key>`. Entries without key (older ones, recipes not saved) show the name, the edit dialog links `url` (own recipes of the recipe app). Push keeps only keys the item has, own recipes and keys already linked in the user's lists (`PlannedRecipe::linkedInListsOf`, so pushing an id gives no access); clients without `key` keep the item's key of the same name/url. Merging planned items joins recipes by key, otherwise name/url (`joinRecipes`); moving keeps them.
- Sorting: options `manual`, `name_asc`, `name_desc`, `newest`, `oldest` (ids are UUID v7 = creation time). Lists overview per user (`preferences.list_sort`), items per list (`shopping_lists.item_sort`, shared). Manual order: `items.position` (shared) and `shopping_list_user.position` (personal, list document field `position`); null positions sort after the positioned ones. Dragging a row writes the shown order as positions (only changed ones) and switches to `manual`.
- Product images: `POST/DELETE /products/{id}/image` (`ImageController`, creates the product if not synced yet), files in `storage/app/private/images/<uuid>` (max. 1200 px, full view) and `<uuid>-thumb` (max. 240 px, rows; older images have none, then the full image is served), served by `GET /images/{uuid}` and `/images/{uuid}/thumb` to the product owner and members of lists with an item using it. The client scales photos to both sizes as WebP/JPEG (`resources/js/image.js`, also drops EXIF), the server accepts max. 700 KB / 100 KB. Tap on a thumbnail opens the full view (`resources/js/lightbox.js`: double tap, pinch and wheel zoom, closes with tap, ✕, Esc or back). The image id is copied to `items.image` (push only accepts images of own products); the service worker caches `/images/*` (CacheFirst).

## Translations

- Languages: `de_CH` (default, Swiss spelling "ss", informal "du") and `en`; keys are the English texts.
- One source for server and client: `lang/de_CH.json` (+ `lang/de_CH/*.php` for Laravel's validation/auth texts from laravel-lang, dev dependency). The app shell translates itself with `$t()` (`resources/js/i18n.js` imports the JSON), Blade pages and mails use `__()`.
- Locale per user (`users.locale`, `PUT /locale`), guests via cookie, otherwise browser language (`SetLocale` middleware). Mails use `HasLocalePreference`.
- After `php artisan lang:update`, replace "ß" by "ss" again and check that the informal texts are kept.

## PWA

- `vite-plugin-pwa` (generateSW) writes `public/sw.js` (not committed, built on deploy).
- Favicons + `public/site.webmanifest`: RealFaviconGenerator via `ddev npm run favicon -- --source src/favicon.png --theme '#047857' --bg '#fafaf9' --padding-bg '#ffd6d6'` (`src/scripts/favicon.mjs`, keeps extra manifest fields). Never use `/icons/`: Apache has a global `Alias /icons/`.
- Updates: `registerType: 'prompt'`; `resources/js/pwa.js` checks for a new service worker on foreground, reconnect and hourly, the app shows "Neue Version verfügbar" and reloads on click (otherwise the new version starts with the next app start).
- Links to server pages in the app shell get `data-online`: dimmed offline, click shows a notice. If a server page is still opened offline, the app shell shows the `offline` view (any path other than `/`).
- The service worker precaches the app shell `/`, build assets and favicons (one 404 aborts the install!); other navigations fall back to the app shell offline.

## UI patterns

- Install instructions: `resources/js/install.js` (platform detection, steps per OS/browser, native `beforeinstallprompt` button), first visit hint + `#/install` view, linked in the settings.

- Rows use `<x-swipe-row actions="…">` (`resources/js/swipe.js`): on touch either swipe left to reveal the actions (no full swipe action) or long press for the actions menu, per user setting `preferences.row_actions` (`users.preferences` JSON, `PUT /preferences`, `resources/js/prefs.js`: cached in localStorage and resent when offline). Mouse gets a hover "…" menu (`pointer-fine`/`pointer-coarse`) and the right-click menu. Actions are defined once in `listActions()`/`itemActions()`/`catalogActions()`.
- Suggestions: `suggestField` (`resources/js/suggest.js`) + `<x-suggestions>` instead of `<datalist>`, sources `item` (quick entry: units right after the amount, picking one keeps typing; then products, picking one adds the item), `product` and `unit` (lists all on focus). Accent-insensitive, ranked exact > prefix > word start > anywhere, then by usage counted from the current items. Adding a product that is already open on the list asks to increase the amount (same unit only) or add anyway. Own products/units: `#/products`, `#/units` (rename to an existing name deletes the renamed one); new units from the edit dialog are stored. `#/products` can add own products and export/import them as CSV (one column `name`, client only: `csvFirstColumn`/`csvValue`; import adds missing names or replaces all own products, names of standard products are skipped; photos are not exported). Items move to another list as a copy with a new id plus deleting the original (`moveItem`), because the server keeps an item in its list; undo removes the copy (`undo.schedule(..., restore)`).
- Item rows (`<x-item-row>`, open and done): the checkbox is its own button (44 px hit area, `role="checkbox"`, labelled with amount and name) and checks off; a tap on the rest of the row (a button labelled "Edit …") opens the edit dialog; the thumbnail is a separate button for the lightbox; the recipe links are a line below the row button (no interactive elements nested), the rest of that line edits too. The swipe row's `guardClick` swallows the click after a swipe, long press or drag.
- Row gestures (`resources/js/swipe.js` + `drag.js`): touch hold and move drags a row (rows with `data-sort-id`, event `row-move` → `moveRow()`), mouse drags directly; hold and release opens the menu in the long-press setting. While a row is held, `touchmove` is prevented to block scrolling.
- Deletions are undoable (`resources/js/undo.js`): rows are hidden, the RxDB remove runs after 5 s or when the app is hidden. Never revive deleted documents.

## Week planner (AI) and recipe app

- Navigation: with the assistant (`/me` `assistant`, verified) the header shows tabs Shopping lists (`#/`), Week planner (`#/planner`), Recipes (`#/recipes`), without it no tabs; tab pages have no back button. Tabs are siblings: from the lists a tab is pushed, between other tabs `openFromLists` goes back to the lists entry first and then pushes the tab (`navAfter`), so back from any tab leads to the lists and then out of the app; the planner opens a created list the same way. The header back button goes up in the structure (`backLink`); `goBack` uses `history.back()` when that is the previous entry (`navStack`), otherwise `location.replace`, so the system back gesture follows the structure too. `navigate(target)` goes back with `history.go(-n)` (`navPops`) if the target is an earlier entry, otherwise pushes (or replaces). Dialogs (`.dialog`) scroll inside when the window is low. Open dialogs and the context menu get a history entry with the same URL (`resources/js/layers.js`), so back closes them first. Pull-to-refresh stays on; a held row blocks it and scrolling with a non-passive `touchmove` listener on the row (`<x-swipe-row>`, must exist from touchstart on, Chrome ignores `preventDefault` of listeners added later) plus `html.row-held` (`overscroll-behavior-y: none`).
- Week planner (`resources/views/partials/planner.blade.php`, `resources/js/planner.js`): four steps, each a page and history entry: `#/planner/offers` (images, PDF, text) → `#/planner/pantry` (photos, optional) → `#/planner/recipes` (suggestions; one big button, servings/count/wishes/AI ideas in a collapsed "Options") → `#/planner/list` (into a new or existing list). `#/planner` opens the last used step (`shoppinglist.planner-step`, device only). Step indicator on top (clickable, "Start over" with confirmation), fixed bar with Back/Next at the bottom. Gating in `resources/js/planner-state.js` (`stepAllowed`: recipes need selected offers, pantry items or planned recipes, the list needs planned recipes or a built list); a step that is not allowed is replaced by the last allowed one. "Start over" keeps the planned recipes (saved on the server) and clears offers selection, pantry, suggestions and items. Jumping forward pushes the skipped steps first (`stepTrail`), going back uses `history.go`, so the back gesture goes back one step. Shown for verified users when `OPENAI_API_KEY` is set (`/me` `assistant`).
- Planner state: localStorage (`shoppinglist.planner`, cache and offline) plus the server (`planner_states`: one JSON row per user, `updated_at` = client ms; `GET/PUT /planner/state`, `PlannerStateController`, max. 1 MB). Last write wins by the client's time (the server keeps the newer one, caps times in the future, returns the current state with `accepted`). Synced: `SYNCED_KEYS` (`offerIds` = selected offers of the pool, pantry items, options, unsaved suggestions, list items, `builtRecipes` = the recipes the items were built from with their saved id, target); not synced: busy/errors/warnings, the step, the planned recipes (`shoppinglist.planned`, a cache of `GET /planned-recipes`); older states are converted by `migrateState` (taken and selected offers → `offerIds`, suggestion selection dropped); data URLs are dropped (pantry photos are never stored, only the recognized items). Client: change → `shoppinglist.planner-sync` `{updated_at, pending}` → PUT after 1 s; opening the planner, foreground and online pull (newer server state replaces the local one) and send pending changes. Only for the device's owner (`shoppinglist.owner`), removed with the local data on logout/account switch (`clearPlannerState`). Not an RxDB collection: the planner needs a connection anyway. Per-shop instructions for getting the offers (copy text or download the PDF) are a collapsible list in the partial; pasted text is sent in parts of max. 18,000 characters (server limit 20,000). Without a recipe app connection a notice at the top links to `/recipes/connect`.
- Server: `PlannerController` (stateless, the client sends offers/pantry back), `app/Ai/Assistant.php` (prompts + strict JSON schemas), `app/Ai/OpenAiClient.php` (Responses API via `Http`, no SDK; `OPENAI_MODEL` default gpt-6-luna (cheapest model that read the test offers reliably), `OPENAI_REASONING_EFFORT`). One global key for all users (free); keep the client per request so own user keys can be added later. Rate limit `throttle:ai` (60/h per user). Requests may take up to ~2 min (`set_time_limit`, `OPENAI_TIMEOUT`).
- Offers pool (`#/offers`, `resources/js/offers.js`, `OfferController`, `offers` table, server only, no offline sync): own offers plus the ones others shared (`shared`, default on; device setting `shoppinglist.share-offers` for read offers). Reading offers (`POST /planner/offers`, also used by the offers page) saves them in the pool and returns them with ids; the same offer (shop, name, brand, end date) is not added twice. Only the creator may edit or delete. Step 1 shows all offers of the pool by shop (collapsible, checkbox per offer, "All"/"None" per shop); a search above (`offerSearch`, device only, not synced; `offerMatches` in `helpers.js`: every word in name or brand, accent-insensitive, also used by `#/offers`) shows only the matching offers, opens their shops and "All"/"None" apply to the shown ones; only ticked ones are used, new ones of the pool start unticked, offers read in the planner are ticked. Expired or deleted offers drop out of the selection (`selectedOfferIds`, ids not in the pool are dropped on the next change). `DELETE /offers` with `store` deletes the own offers of a shop. Regional offers: shops whose offers differ by region are listed in `App\Support\ShopRegions` (only Migros, its ten cooperatives; Coop's offers are national; remove the Migros entry if the cooperatives merge as planned for 2027). Offers have `region` (null: everywhere; dropped if it does not belong to the shop); the AI reads it from the material, otherwise read offers get the user's region of the shop. Users pick a region per shop in the settings (`preferences.regions`, tag => key; `/me` `regions` lists them); `Offer::visibleTo` then hides shared offers of the shop's other regions. Without a chosen region all regions are shown (with a hint on `#/offers`). Planner steps use `<x-planner-step>` cards. `offers:prune` (daily) removes expired offers and undated ones after `Offer::UNDATED_DAYS`. Shared reading UI: `<x-offer-reader>` with `requests()` + `offerReader()`.
- Seasons (`App\Support\Seasons`): suggestions prefer foods in season in Switzerland this month (fresh harvest, storage does not count). With a connected recipe app its season data (`/api/foods` `season_months`) ranks the candidates (offers, then pantry, then season), `season_month` is sent to its search and the seasonal names go to the AI (`seasonal`); without one (or without season data there) the copy `database/data/food-seasons.php` is used (source of truth: RecipeManager's file of the same name). Shown to the user: `/me` `season` (month + foods from the copy) marks seasonal products in the suggestions with a leaf (`seasonalFood`, same matching as `Seasons::among`), the planner links to the recipe app's season calendar (`<RECIPES_URL>/season`) and each suggestion names its seasonal foods (`uses_season`).
- Recipe suggestions are not saved. Saving is planning: "Plan" (`POST /planned-recipes`) saves one as planned recipe and removes it from the suggestions; step 3 and 4 list the planned recipes (`<x-planned-recipes>`, ✕ = unplan, `DELETE /planned-recipes/{id}/plan`; in step 3 it becomes a suggestion again). A new search replaces the suggestions and leaves out the planned ones (`withoutPlanned`, also excluded from the search); "Suggest more recipes" appends. Step 4 builds the list from all planned recipes; a second build (planned again before adding) appends to the items. Ingredients and shopping list entries use generic names ("Kartoffeln", not "Bio-Kartoffeln"); the offer stays linked (`offer`) and its product name goes into the item note when it differs (`Assistant::offerNote`).
- Shop codes: `Assistant::SHOPS` (the standard shops, keep in sync with the `stores` migration) → `items.stores`; offer details → `items.note`. Own shops are not passed to the AI.
- Recipe app ("white label"): `RECIPES_NAME` (quote values with spaces, e.g. `"Ammanns Best"`), `RECIPES_URL`, `RECIPES_CLIENT_ID`, `RECIPES_CLIENT_SECRET` (Passport client in the recipe app, redirect URI `<APP_URL>/recipes/callback`). OAuth flow in `RecipesConnectionController` (no input at all when the recipe app lists the client in `PASSPORT_TRUSTED_CLIENTS` and both use the same OIDC login; `sso=1` in the authorize URL only for users with `oidc_sub`, others get the recipe app's login form), API calls and token refresh in `app/Recipes/RecipesClient.php`, tokens encrypted in `users.recipes_connection` (`EncryptedArrayOrNull`: a value encrypted with another APP_KEY, e.g. after `ddev pull production`, reads as not connected). API contract: RecipeManager `AGENTS.md`. Locally the client lives in the RecipeManager DDEV database: after `ddev pull production` there it is gone (`invalid_client`); create a new one (`ddev artisan passport:client --name="Shoppinglist (lokal)" --redirect_uri=https://shoppinglist.ddev.site/recipes/callback -n`) and put ID and secret into `.env`.
- Recipes tab (`#/recipes`, `resources/js/recipe-history.js`, `PlannedRecipeController`, `planned_recipes`, server only): groups "Planned" (`planned` true: not on a list yet) and "On a list / earlier". Saved by "Plan" (`POST /planned-recipes`, `StorePlannedRecipeRequest`, sets `planned` and `planned_at` = date of the offers in `uses_offers`, shown as "Aktionen vom 6.11." in the dialog), when building the list (`POST /planner/list` sends the full planned recipes, `recipePayload`; sets `used_at` and `planned` false, so the items' recipe links work) and on import. "Plan again" (`POST /planned-recipes/{id}/plan` with the planner's `offer_ids` and selected pantry names from localStorage, `currentSelection`) sets `planned`/`planned_at` and recomputes `uses_offers`/`uses_pantry` by ingredient names (`App\Support\FoodNames`: main word of the ingredient vs. the words of the product, equal or start/end, no AI) and `uses_season` for the current month (recipe app season data, else the copy); own recipes without saved ingredients load them from the recipe app first. The planner and the tab tell each other by the `planned-recipe` window event. Existing entries were migrated as not planned (`planned_at` = last save). The limit only removes recipes that are not planned. `PlannedRecipe::remember`: own recipes once per recipe id (key `recipe-<id>`), AI ideas by key with ingredients and preparation, max. `PlannedRecipe::LIMIT` per user. Handing an idea to the recipe app (`POST /planner/recipes` with key and all details) saves it first if it is not saved yet (not planned) and sets `draft_url`. `POST /planner/list` returns `recipes: [{key, id}]` (recipe key → saved id, kept in `builtRecipes`, the items get it as `key`, `listRecipes`), maps the item recipe names back to the suggestion names and saves own recipes with the recipe app's ingredients. The tab caches the last loaded recipes (`shoppinglist.recipes`, removed with the local data) and shows per recipe the linked items from RxDB ("3/5 erledigt" in the row, items with list and status in the dialog, tap opens the list). `#/recipes/<id>` replaces itself with `#/recipes` and opens the dialog (back closes it, then leaves the tab): own recipe, else `GET /planned-recipes/{id}` (read only for members of a list with an item linked to it, `toShared` without `draft_url`; others 404), else a stand-in from the items (removed recipe).
- Recipe details: `<x-recipe-dialog>` (Recipes tab and step 3; the component's `detail` + `$refs.recipeDialog`, actions in the slot). Navigating from a dialog uses `closeDialogThen` (`layers.js`), otherwise the pending back of the layer undoes the navigation.
- Adding the planner's items to an existing list asks first if some are already open there with the same unit, or with g/kg resp. ml/cl/dl/l (`plannedMerges`, `mergedAmount` converts into the open item's unit): merging adds the amounts and joins recipes, shops and notes.
- Unit conversion: the recipe app's `/api/recipes/{id}` returns `converted` per ingredient (g/kg or ml/dl/l, from its densities and piece weights). Before the AI builds the shopping list, `App\Recipes\RecipeIngredients::unify()` replaces the amount of a food used with different units across the chosen recipes (1 Tasse Mehl + 200 g Mehl) by its converted g/ml; foods with one unit keep it (2 Stk. Zwiebeln). Recipe apps without `converted` keep their units. AI ideas are not converted.
- Progress and errors are shown at the button that started a request (`run(key, label, action)`, `busyKey`/`errorKey`, `<x-spinner>`, `<x-planner-error>`). "Suggest more recipes" sends the shown ones as `exclude` (recipe ids + names) and appends the new ones unselected.
- Suggestions prefer recipes combining several offers: own recipes are searched by offer foods first, then pantry foods, and sorted by matched offers. With a connected recipe app, AI ideas use its categories, units and complexities (`GET /api/vocabulary`).
- AI ideas are never saved directly: "Import into …" posts them as a draft (`POST /api/recipe-drafts`, recipe import JSON) and opens the returned import wizard URL in a new tab, where the user matches foods, units and the category and picks cookbook and visibility. Unknown values can be omitted there, or requested (admins approve them).
- Tests fake OpenAI and the recipe app with `Http::fake()` (`tests/Feature/PlannerTest.php`).

## Gotchas

- After renaming/moving the project, Blade may serve stale compiled views (Mutagen keeps old mtimes): `ddev artisan optimize:clear`.
- After renaming the DDEV project, delete the old `.ddev/traefik/{certs,config}/<old-name>.*` files: `.ddev/.gitignore` only ignores the certificates of the current name, so dev keys would end up in a commit.
- `node` on the host may be a Docker wrapper; use `ddev npm …` or `~/.openclaw/tools/node-*/bin/node` for host scripts.

## Rules

- Alpine proxies (e.g. arrays from `x-model` state) must be copied to plain values before `insert`/`incrementalPatch`: RxDB clones documents for the BroadcastChannel (DataCloneError).
- Every synced field must exist in the RxDB schema (`resources/js/db/schemas.js`), the resource document and the push validation (`SyncController`). Schema changes in RxDB need a schema version bump and migration strategy. Migration strategies keep values already present (`{ field: default, ...doc }`). If the server already fills the new field when the client updates, also bump the collection in `REPLICATION_RUNS` (`resources/js/db/index.js`): the old app version keeps syncing until the update is accepted, pulls the field without knowing it and moves its checkpoint past it; the new run pulls the collection again.
- Keep the app shell (`resources/views/app.blade.php`) free of user data, it is cached by the service worker.
