# AGENTS.md

Shoppinglist: offline-first PWA for shared shopping lists. One Laravel app serves the UI and the sync API.

## Stack

- Laravel 13, PHP 8.4, MariaDB 10.11, DDEV (`shoppinglist.ddev.site`). Run PHP/Composer/Artisan/npm via `ddev`.
- Auth: Fortify (session cookie, Blade views in `resources/views/auth`), email verification required for syncing. Passkeys via Fortify + `laravel/passkeys` (client `@laravel/passkeys`: login/confirmation in `resources/js/auth.js`, managing in `resources/js/account.js`); adding and removing them requires a password (or passkey) confirmation. No account page: "Manage account" at the bottom of the settings (see «Manage account in the settings»).
- Frontend: Blade + Alpine.js + Tailwind 4 (Vite). No SPA framework, no Livewire (must work offline).
- Client database: RxDB (Dexie/IndexedDB storage) with HTTP replication.
- Hosting target: shared hosting with KeyHelp (PHP-FPM + cron, no long running processes, no websockets). Cron every minute: `schedule:run` and `queue:work --max-time=50` (like RecipeManager).

## Optional OpenID Connect login (SSO)

- Off by default; any OIDC provider works (Laravel Socialite + `kovah/laravel-socialite-oidc`, JWT signature verified). Settings in `config/login.php` (`AUTH_LOCAL_*`, `AUTH_OIDC_*`) and `config/services.php` (`oidc`: issuer, client id/secret); same structure as RecipeManager and Chorelist. `App\Auth\OidcProvider` additionally checks `iss`, `aud`/`azp` and `exp` (`OidcClaims`).
- Routes `/auth/oidc/redirect`, `/auth/oidc/callback` (`OidcController`, intents `login`, `link`, `confirm`; redirect URI for the provider: `<APP_URL>/auth/oidc/callback`), link `POST /account/oidc`, unlink `DELETE /account/oidc` (JSON for the settings). Matching in `App\Auth\OidcLogin`: by `users.oidc_sub`, otherwise by email only if the provider marks it as verified (an unverified local account gets verified; somebody else may have registered or been invited with the address, linking drops their password, passkeys and sessions). Unknown users get a verified account without password (`AUTH_OIDC_REGISTRATION`); `AUTH_OIDC_REQUIRED_GROUP` checks the `groups` claim. The login stays remembered like the password login.
- `AUTH_LOCAL_ENABLED=false` (`RestrictLocalLogin` middleware): the login page shows only the OIDC button (`/login?local=1` shows the form), password logins only for `AUTH_LOCAL_EMERGENCY_EMAILS`, passkey logins are off. `AUTH_LOCAL_REGISTRATION=false` removes Fortify's registration. Password reset stays for unlinked accounts (users without password set one; needed for changing the password and managing passkeys).

### Linked accounts are SSO-only (same rules as RecipeManager and Chorelist)

- A linked account (`oidc_sub` set, `User::isLinkedToOidc()`) logs in through the provider only. All rules live in `App\Auth\OidcAccount` (reference: RecipeManager `AGENTS.md`, «Linked accounts are SSO-only»; same implementation as Chorelist); `User::booted()` throws if a linked account would get a password, `FortifyServiceProvider` if it would get a passkey (link/unlink only through `OidcAccount`, the factory drops the password of `linked()` users).
- Linking (first OIDC login matched by email, or "Link …" in the settings) = `OidcAccount::link()`: password null, passkeys deleted, remember token rotated, password reset tokens deleted, the user's other sessions deleted (database session driver only; other drivers: they run out after `SESSION_LIFETIME`, `AuthenticateSession` skips users without password), then the callback logs in again with a new remember cookie. Lists, households, preferences, the planner and the recipe app connection stay (the connection to the recipe app is its own OAuth token, not touched).
- "Link …" in the settings first asks for the current password in a dialog (`POST /account/oidc`, JSON `{redirect}`, `throttle:5,1`; accounts without one skip it): it stores `oidc.password_confirmed_at`, `/auth/oidc/redirect?link=1` needs it (5 min, used once), otherwise back to the settings with the message.
- Local login: the Fortify login pipeline (`Fortify::authenticateThrough`, Fortify's default steps plus `App\Actions\Fortify\RefuseLinkedAccounts` before the password check) refuses linked accounts (also with a leftover password) with "This account is connected to :provider. Sign in with :provider." (same key as RecipeManager) («Dieses Konto ist mit :provider verbunden. Melde dich mit :provider an.», `OidcAccount::message()`); `RestrictLocalLogin` answers the same with the local login disabled. Passkey logins of linked accounts (only leftover passkeys) are refused with the same message (`Passkeys::authorizeLoginUsing`); `auth.js` also shows it for the email field's autofill. Enumeration: this only adds "linked or not" for addresses whose account exists, which registration ("already taken") and the reset page ("can't find a user") tell anyway; unknown addresses and wrong passwords keep `auth.failed`, the login stays rate limited.
- Password reset (`App\Http\Controllers\Auth\PasswordResetLinkController`/`NewPasswordController`, bound in place of Fortify's): a linked account gets no token but the mail `SignInWithOidcNotice` (once per 15 min, not queued like the reset link) and the page answers like for any account (also "wait" within the broker's 60 s throttle); a valid reset link of a linked account (e.g. older than the link) is refused with the message above and its token deleted; an invalid token keeps the usual answer. Invitations to lists by email create accounts without `oidc_sub`, so they keep the reset link.
- Unlinking (only with the OIDC login enabled) = `OidcAccount::unlink()`: needs an OIDC login within 15 min (`oidc.signed_in_at`, set by every login/link/confirmation). Otherwise "Unlink from …" in the settings goes to `/auth/oidc/redirect?confirm=1` first (also a `DELETE` without it: 409 `{redirect}`); the callback checks that the provider returns the same `sub` and redirects to `/?account=unlink#/settings`, which opens the dialog again. The dialog takes a new password + confirmation (`PasswordValidationRules`); unlinking sets it, rotates the remember token, ends the other sessions and moves mirrored households to pending (AccountManager driver: `AccountManagerHouseholds::detachUser`, before `oidc_sub` is cleared; the user's own lists are unshared from them like leaving). The provider may confirm without a prompt while the user is still logged in there.
- Settings: linked accounts get "Unlink from …" and (AccountManager connected) "Manage account in “…”" instead of e-mail, password and passkeys; Fortify's `PUT /user/profile-information` keeps the email of a linked account (`UpdateUserProfileInformation`). Deleting a linked account needs the same recent OIDC login instead of the password (`?confirm=1&for=delete` → `/?account=delete#/settings`); with the OIDC login disabled it is not possible (`users:unlink-oidc`, then "Forgot your password?").
- Results of the redirects (linked, a failed link or confirmation) are put into the session (`AccountController::NOTICE`) and handed out once by `/me` (`notice`): the cached app shell cannot render the session.
- Existing data: migration `2026_11_10_090000_remove_local_login_from_linked_accounts` (passwords, passkeys, remember tokens, reset tokens and sessions of linked accounts; linked users log in again once). Unlinked accounts are untouched; accounts without password and without `oidc_sub` can still use "Forgot your password?".
- Emergency addresses (`AUTH_LOCAL_EMERGENCY_EMAILS`) must stay unlinked (with `AUTH_LOCAL_ENABLED=false` they are the only password login). Way back (provider gone, lost provider account): `users:unlink-oidc {emails*} {--all}` unlinks without password (mirrored households become pending), the users then use "Forgot your password?".
- Tests: `OidcLinkedAccountTest` (shared Socialite mock `Tests\Feature\Concerns\MocksOidcProvider`).
- Temporary diagnostics (users signed out after a while): `LogRejectedRememberCookie` logs why a remember cookie did not sign in (reason, path, IP, user agent; once per cookie and 10 min), `User::booted()` logs every `remember_token` change (sha256 fingerprints, trace, request or command). Tests `AuthDiagnosticsTest`. Remove all of it once the cause is found.

## Sync architecture

- The UI reads and writes only the local RxDB database; replication runs in the background (`resources/js/db`).
- Server side: `app/Sync/*Resource.php` implement pull (checkpoint `updated_at` + id) and push (conflict detection) per collection, routes `GET /sync/{collection}/pull`, `POST /sync/{collection}/push`.
- IDs are UUIDs generated on the client. Timestamps have millisecond precision (`Syncable` trait).
- Conflicts: every local change increases `version` (RxDB `preSave` hook); the server accepts a push only if `assumedMasterState.version` equals its version and keeps the client's version. Otherwise it returns its document and the server state wins.
- Lists are pulled via memberships (`shopping_list_user`), so revoked access and deleted lists arrive as deleted documents. Any list change has to call `touchForMembers()`; adding a member also touches the items.
- Access to a list: shared by email (or own, `shopping_list_user.direct`) or shared with a household of the user (`shopping_list_household` + `household_user`), resolved at runtime in `User::accessibleListIds()` (items pull/push, images, list pushes). Household members get a sync row too (`shopping_list_user` with `direct` false, keeps their personal `position`): `ShoppingList::syncHouseholdAccess()` creates/restores/deletes these rows and has to run after every change of the shares or of the members of a shared household (`Household::addMember`/`removeMember`/`deleteWithShares`, `shareWith`/`unshareWith`), so removed members get the list as deleted document with the next pull. See "Households".
- Items of a list unknown to the server return 409, the client retries (list created offline, not pushed yet).
- Sharing/leaving lists needs a connection (`MemberController`, `ListHouseholdController`). Unknown emails get an account and a password-reset invitation.
- Products, units and shops (`CatalogResource`): own entries per user, public ones (no owner) are read only. Shops (`stores`: name + optional code, max. 10 chars, case kept, `icon`, `countries`): standard shops from `database/data/standard-stores.php`, synced by `shoppinglist:standard-stores` (`--dry-run`; adds/updates, removes unlisted ones, deletes own shops with a standard shop's name or code and retags their owner's items; when the list changes, add a migration that calls it again). Only Migros M, Coop C, Aldi A, Lidl L, Denner D have codes (week planner). Icons: standard shops name a file in `resources/images/shops` (SVG if the shop's mark exists as one, else a small PNG; built and precached by Vite, `resources/js/stores.js`), own shops may have a small image as data URL in the document (max. 64 px, raster only, `StoreResource::ICON_PATTERN`); the badge (`<x-store-badge>`) shows the icon, otherwise the tag. The shop choice only offers standard shops of the user's country (`preferences.country`: CH/DE/AT, set from the device's time zone/language without a location request, existing users CH) and sorts by usage, recent items weighing more (`storeUsage`). Items keep their shops as tags in `items.stores` (JSON list: the code, or the name of a shop without code; copied like `image`, so members of shared lists see them), the badge shows the shop name as tooltip. Names and codes must not collide (both are tags). The edit dialog picks shops as chips (`suggestField` source `store`), an unknown typed one becomes an own shop without code; changing an own shop's tag updates the items. Own shops are managed in `#/stores`; standard shops can be hidden from the shop choice per user (`preferences.hidden_stores`, tags; older entries are codes, which are the tags). A shop picker before the quick entry (`newItemStore`, native select on top of the badge, most used first) sets the shop of new items until changed. Lists can be filtered by shop on the device (`shoppinglist.store-filter`; items without shop stay visible, dragging while filtered moves next to the target row). Pushes from older clients with `store` (one code) and without `recipes` keep working (`ItemResource::attributes`).
- Standard products: public products from `database/data/standard-products.csv` (name, category for review only), synced by `shoppinglist:standard-products` (`--dry-run`): adds missing, removes unlisted ones and deletes own duplicates without image. Run by a migration; when the list changes, add a new migration that calls it again. An own product with the name of a standard product only carries the user's photo: the products view shows the standard product with it, removing the photo deletes the own copy.
- `items.recipes`: recipes the item was planned for (`[{name, url, key}]`, `resources/js/recipe-links.js`). `key` = id of the saved recipe (`planned_recipes`): the name in the row (a link below the row button, not inside it, also on done rows) and in the edit dialog opens `#/recipes/<key>`. Entries without key (older ones, recipes not saved) show the name, the edit dialog links `url` (own recipes of the recipe app). Push keeps only keys the item has, own recipes and keys already linked in the user's lists (`PlannedRecipe::linkedInListsOf`, so pushing an id gives no access); clients without `key` keep the item's key of the same name/url. Merging planned items joins recipes by key, otherwise name/url (`joinRecipes`); moving keeps them.
- Sorting: options `manual`, `name_asc`, `name_desc`, `newest`, `oldest` (ids are UUID v7 = creation time). Lists overview per user (`preferences.list_sort`), items per list (`shopping_lists.item_sort`, shared). Manual order: `items.position` (shared) and `shopping_list_user.position` (personal, list document field `position`); null positions sort after the positioned ones. Dragging a row writes the shown order as positions (only changed ones) and switches to `manual`.
- Product images: `POST/DELETE /products/{id}/image` (`ImageController`, creates the product if not synced yet), files in `storage/app/private/images/<uuid>` (max. 1200 px, full view) and `<uuid>-thumb` (max. 240 px, rows; older images have none, then the full image is served), served by `GET /images/{uuid}` and `/images/{uuid}/thumb` to the product owner and members of lists with an item using it. The client scales photos to both sizes as WebP/JPEG (`resources/js/image.js`, also drops EXIF), the server accepts max. 700 KB / 100 KB. Tap on a thumbnail opens the full view (`resources/js/lightbox.js`: double tap, pinch and wheel zoom, closes with tap, ✕, Esc or back). The image id is copied to `items.image` (push only accepts images of own products); the service worker caches `/images/*` (CacheFirst).

## Households

- `config/households.php`, `HOUSEHOLDS_DRIVER`: `local` (default, managed in this app) or `account-manager` (mirrored from the AccountManager, see below; the local management is read only, `Household::managedLocally()` + `HouseholdPolicy`). Same design as RecipeManager and Chorelist: `households` (`uuid`, `name`, `created_by`, `account_manager_household_uuid`, `account_manager_version`, `account_manager_import_status`, `account_manager_shares_hash`), `household_user` (`role` admin|member, `joined_at`), `household_invitations` (`token_hash` = sha256 of the token in the mail, `expires_at` after `invitation_days`, `accepted_at`), `household_pending_members` (mirrored members without a user yet), `account_manager_webhook_events` (processed event ids, 7 days).
- Roles: admins rename/delete the household, invite, change roles and remove members; members leave. At least one admin remains (`Household::isLastAdmin`). Removing a member (or leaving) also ends the shares of that member's lists with the household; deleting the household removes shares and memberships only, lists stay with their owners.
- Page (server rendered, needs a connection, linked in the settings): `/households` (`HouseholdController`, `HouseholdMemberController`, `HouseholdInvitationController`) lists all households of the user as `<details>` (`households/household.blade.php`, same page as in Chorelist): collapsed name, role, member count and AccountManager status, opened members, invitations, shared lists and actions. Actions redirect to `/households#household-<uuid>` with `household` in the session (`Controller::toHousehold`), forms send `_household` so a failed validation opens it again; a single household is always open. `/households/{uuid}` (old links) redirects there. Invitation link `/households/invitations/{token}` (also for guests: stores `url.intended`, they log in or register and come back); accepting needs the invited address and verifies it. Open invitations for the user's verified address (`User::householdInvitations()`, local driver only) are listed on top of `/households` ("Invitations for you", accept `POST /households/invitations/{id}/accept`, decline `DELETE /households/invitations/{id}`, like Chorelist); `/me` `household_invitations` counts them for the badge in the settings.
- "Share with household" in the share dialog of the app (owner only, households the owner belongs to, both drivers): `POST /lists/{list}/households` (`household` uuid), `DELETE /lists/{list}/households/{uuid}` (`ListHouseholdController`). `/me` `households` lists the user's households. List documents: `households` (`[{id: uuid, name}]`, owner: all shares, members: their households), `members` only the members shared by email. Members with access through a household cannot leave the list (no action; a pushed deletion returns the list as conflict), they leave the household.
- Tests: `tests/Feature/HouseholdTest.php` (access, sync pull/push after removal, recipes linked in household lists, last admin, invitations, `account-manager` driver read only), `tests/Feature/AccountManagerHouseholdTest.php` (mirroring, `Http::fake` AccountManager).

### Households from the AccountManager (`HOUSEHOLDS_DRIVER=account-manager`)

- Contract: AccountManager `docs/HOUSEHOLDS-API.md` (phase 8 of its concept). Env `ACCOUNT_MANAGER_URL`, `ACCOUNT_MANAGER_SERVICE_KEY`, `ACCOUNT_MANAGER_SECRET` (one secret signs the webhooks and authenticates the API with HTTP Basic), `ACCOUNT_MANAGER_REPORT_SHARES`. Needs the OIDC login (members are matched by `oidc_sub`). Mirroring is active only with the driver and all three values (`AccountManagerHouseholds::enabled()`), otherwise the webhook returns 404. Same implementation as Chorelist.
- `App\Households\AccountManagerClient` (API: `GET /api/households?sub=`, `GET /api/households/{uuid}`, `PUT …/shares`, `POST/GET /api/households/import`; every failure is `AccountManagerUnavailable`, 404 is an answer), `AccountManagerHouseholds` (applying snapshots), jobs `ApplyAccountManagerEvent`, `ReportAccountManagerShares`.
- Webhook `POST /api/account-manager/webhook` (`routes/api.php`, no session/CSRF, `throttle:120,1`, `Api\AccountManagerWebhookController`): HMAC-SHA256 over `"{timestamp}.{body}"` (raw body, `X-Account-Manager-Signature`, `X-Account-Manager-Timestamp` max. 300 s off), accepted once per `event_id` (`account_manager_webhook_events`, `model:prune` after 7 days), applied by the queued `ApplyAccountManagerEvent`. Always 204 for duplicates, stale and unknown types.
- Every event and API answer is a full snapshot: name, members by `oidc_sub` (unknown subjects → `household_pending_members`, attached on the first OIDC login), roles, all other members removed (`Household::detachMembers`: their own lists are unshared, like leaving). Webhooks apply only `version > account_manager_version`, API answers always apply (current truth, also with a lower version, e.g. after a backup restore of the AccountManager). `household.deleted` → `deleteWithShares()` (lists stay with their owners). Events of unknown households are confirmed with `GET /api/households/{uuid}` (404: nothing is created; AccountManager down: the job is retried). Member changes run `Household::syncListAccess()` (sync rows of all shared lists), a rename `touchLists()`, so clients gain or lose lists on the next pull.
- `households:sync` (daily 04:15): `GET /api/households?sub=` for every user with `oidc_sub`, mirrored households nobody listed are checked one by one (404 deletes). The OIDC login (and linking) attaches pending memberships and syncs the user; unlinking (also `users:unlink-oidc`) moves the user's memberships back to pending. AccountManager down: last state stays, warning in the log, the login works.
- Shares (optional, `ACCOUNT_MANAGER_REPORT_SHARES`): `ReportAccountManagerShares` sends the lists shared with a mirrored household (`shopping_list`, list id, name) after sharing/unsharing, renaming, deleting or restoring a list and in the daily sync; only changes (`account_manager_shares_hash`), failures are ignored.
- Switching from `local`: set the driver and the AccountManager values, run `households:import`: proposes the local households without `account_manager_household_uuid` (members with `oidc_sub` only; households without any are skipped). An admin of the AccountManager confirms; the hourly `households:import --check` maps confirmed ones (`account_manager_household_uuid`, name and members from the snapshot, shares stay; if the household is mirrored already the shares move there and the local one is dropped) and marks rejected ones (`account_manager_import_status`, stay local and read only). Members without a linked login lose the household access on confirmation.
- Back to `local`: mirrored households become ordinary local households (management enabled again, `account_manager_household_uuid`/`account_manager_version` stay, pending members are ignored), shares stay. Switching to `account-manager` again overwrites them with the next newer snapshot.
- UI texts name the AccountManager ("Manage households in “:name”", "Only in this app, not managed in “:name”." …): `App\Households\AccountManagerLabel::get()` = `ACCOUNT_MANAGER_LABEL`, otherwise the `name` (its `APP_NAME`) from the public `ACCOUNT_MANAGER_URL/api/info` (only asked with the account-manager driver; cached a day, a failure 10 minutes), otherwise "Account" («Konto»). The link goes to `AccountManagerHouseholds::portalUrl()` (`households_url` of `/api/info`, otherwise `ACCOUNT_MANAGER_URL/households`). Tests: `AccountManagerLabelTest`.

- Easter egg: "All rights reserved." in the mail footer (published `resources/views/vendor/mail/{html,text}/message.blade.php`, nothing else of the mail views) links to `<ACCOUNT_MANAGER_URL>/easter-egg` (the page and the video live only in the AccountManager) via `App\Support\EasterEgg::url()`; without `ACCOUNT_MANAGER_URL` it stays plain text. Tests: `EasterEggMailTest`.

## Entitlements from the AccountManager

- Contract: AccountManager `docs/ENTITLEMENTS-API.md` (phase 6a), concept 5.3/6. Same design and names as RecipeManager
  (reference, its `AGENTS.md` «Entitlements from the AccountManager») and Chorelist. `config/entitlements.php`: `driver`
  (`ENTITLEMENTS_DRIVER`, `local` default), `admin_source` (`AUTH_ADMIN_SOURCE`, `local` default), `local.features`
  (`ENTITLEMENTS_LOCAL_FEATURES`, comma separated, default `shoppinglist.ai`); uses the `ACCOUNT_MANAGER_*` values, the
  client (`AccountManagerClient::entitlements()`, `GET /api/entitlements/{sub}`, 404 = no access) and the webhook of the households.
- `App\Entitlements\Entitlements` (static): `has($user, 'key')`, `features()`, `isAdmin()`, `status()`, `allowsAccess()`.
  Local driver: everybody has access and the local features. Account-manager driver: linked users (`oidc_sub`) get the stored
  snapshot (features only while `active`; never synced = access, no features), unlinked users keep the local features.
- AI: `OpenAiClient::enabledFor($user)` = key set and `shoppinglist.ai`. `/me`: `features`, `assistant` (enabled for the
  user: tabs, planner, recipes), `assistant_locked` (key set, feature missing: the settings and the planner show «Die
  KI-Funktionen sind für dein Konto nicht freigeschaltet.»). `EnsureAiFeature` on the `planner.*` routes (all AI calls:
  offers, pantry, suggestions, list, recipe drafts) answers 403 with that message; planned recipes, the planner state and
  the offers pool need no AI and stay open. The local driver keeps the old switch (key set = AI for all, unless
  `ENTITLEMENTS_LOCAL_FEATURES` leaves it out).
- Admin: the app has no admin features; `Entitlements::isAdmin()` is prepared (emergency addresses = admins,
  `AUTH_ADMIN_SOURCE=account-manager`: the snapshot's admin flag for linked users) and unused.
- Storage: `user_entitlements` (user_id unique, status, admin, features JSON, version, synced_at; `User::entitlement()`), dropped
  when `oidc_sub` changes (`User::booted()`). `App\Entitlements\AccountManagerEntitlements`: webhooks apply only
  `version > stored`, API answers always apply (current truth, also with a lower version, e.g. after a backup restore of the AccountManager); 404 sets `none` and keeps the version; unknown subjects are ignored (the OIDC
  login fetches the snapshot: `syncOnSignIn()`, 5 s, failures keep the last state and log a warning). `entitlements:sync`
  (daily 04:30) for every linked user. Stored when the driver or the admin source is `account-manager` and configured.
- Webhook `POST /api/account-manager/webhook`: open with mirrored households or synced entitlements, otherwise 404;
  `entitlements.changed` applied right away (with the `event_id` row in one transaction; `service` must be ours, else 422),
  `user.deleted` queued (`DeleteAccountManagerUser`), unknown types 204.
- Access (driver account-manager): `EnsureEntitlementAccess` (web group) blocks linked users with status `suspended`,
  `requested` or `none`. JSON requests (`/me`, sync, planner …) get 403 `{message, access: suspended|disabled}` and keep the
  session; page requests sign out and show «Dein Zugang zu :app ist gesperrt.» / «… ist nicht freigeschaltet.» on the login
  page. The PWA (`isBlocked()`/`block()` in `app.js`) sets the sync status `blocked` (from `/me` or a replication error),
  shows the message, stops syncing and keeps the local data. The OIDC callback refuses blocked users after the sync.
- `user.deleted` = `App\Services\UserDeletion`, the same code as "Delete account" in the settings (`AccountController::destroy`): own lists without other members are
  deleted, shared ones go to another member (shared by email first, then through a household, the longest first; the
  new owner gets a direct membership); memberships in other lists end like leaving; households are left (local: an
  admin-less one goes to its longest member, an empty one is deleted; mirrored: only leaving); products, shops, offers,
  planned recipes, planner state, passkeys go with the user (FK cascades), sessions (database driver) and photos of own
  products unless items still show them. Removing the access is no deletion (`status: none`).
- Tests: `AccountManagerEntitlementsTest`.

## PWA

- `vite-plugin-pwa` (generateSW) writes `public/sw.js` (not committed, built on deploy).
- Favicons + `public/site.webmanifest`: RealFaviconGenerator via `ddev npm run favicon -- --source src/favicon.png --theme '#047857' --bg '#fafaf9' --padding-bg '#ffd6d6'` (`src/scripts/favicon.mjs`, keeps extra manifest fields). Never use `/icons/`: Apache has a global `Alias /icons/`.
- Updates: `registerType: 'prompt'`; `resources/js/pwa.js` checks for a new service worker on foreground, reconnect and hourly, the app shows "Neue Version verfügbar" and reloads on click (otherwise the new version starts with the next app start).

## Week planner (AI) and recipe app

- Navigation: with the assistant (`/me` `assistant`, verified) the header shows tabs Shopping lists (`#/`), Week planner (`#/planner`), Recipes (`#/recipes`), without it no tabs; tab pages have no back button. Tabs are siblings: from the lists a tab is pushed, between other tabs `openFromLists` goes back to the lists entry first and then pushes the tab (`navAfter`), so back from any tab leads to the lists and then out of the app; the planner opens a created list the same way. The header back button goes up in the structure (`backLink`); `goBack` uses `history.back()` when that is the previous entry (`navStack`), otherwise `location.replace`, so the system back gesture follows the structure too. `navigate(target)` goes back with `history.go(-n)` (`navPops`) if the target is an earlier entry, otherwise pushes (or replaces). Dialogs (`.dialog`) scroll inside when the window is low. Open dialogs and the context menu get a history entry with the same URL (`resources/js/layers.js`), so back closes them first. Pull-to-refresh stays on; a held row blocks it and scrolling with a non-passive `touchmove` listener on the row (`<x-swipe-row>`, must exist from touchstart on, Chrome ignores `preventDefault` of listeners added later) plus `html.row-held` (`overscroll-behavior-y: none`).
- Week planner (`resources/views/partials/planner.blade.php`, `resources/js/planner.js`): four steps, each a page and history entry: `#/planner/offers` (images, PDF, text) → `#/planner/pantry` (photos, optional) → `#/planner/recipes` (suggestions; one big button, servings/count/wishes/AI ideas in a collapsed "Options") → `#/planner/list` (into a new or existing list). `#/planner` opens the last used step (`shoppinglist.planner-step`, device only). Step indicator on top (clickable, "Start over" with confirmation), fixed bar with Back/Next at the bottom. Gating in `resources/js/planner-state.js` (`stepAllowed`: the recipes step is always open (own recipes need no offers; "Suggest recipes" needs selected offers or pantry items), the list needs planned recipes or a built list); a step that is not allowed is replaced by the last allowed one. "Start over" keeps the planned recipes (saved on the server) and clears offers selection, pantry, suggestions and items. Jumping forward pushes the skipped steps first (`stepTrail`), going back uses `history.go`, so the back gesture goes back one step. Shown for verified users when `OPENAI_API_KEY` is set and the feature `shoppinglist.ai` is unlocked (`/me` `assistant`, see «Entitlements from the AccountManager»).
- Planner state: localStorage (`shoppinglist.planner`, cache and offline) plus the server (`planner_states`: one JSON row per user, `updated_at` = client ms; `GET/PUT /planner/state`, `PlannerStateController`, max. 1 MB). Last write wins by the client's time (the server keeps the newer one, caps times in the future, returns the current state with `accepted`). Synced: `SYNCED_KEYS` (`offerIds` = selected offers of the pool, pantry items, options, unsaved suggestions, list items, `builtRecipes` = the recipes the items were built from with their saved id, target); not synced: busy/errors/warnings, the step, the planned recipes (`shoppinglist.planned`, a cache of `GET /planned-recipes`); older states are converted by `migrateState` (taken and selected offers → `offerIds`, suggestion selection dropped); data URLs are dropped (pantry photos are never stored, only the recognized items). Client: change → `shoppinglist.planner-sync` `{updated_at, pending}` → PUT after 1 s; opening the planner, foreground and online pull (newer server state replaces the local one) and send pending changes. Only for the device's owner (`shoppinglist.owner`), removed with the local data on logout/account switch (`clearPlannerState`). Not an RxDB collection: the planner needs a connection anyway. Per-shop instructions for getting the offers (copy text or download the PDF) are a collapsible list in the partial; pasted text is sent in parts of max. 18,000 characters (server limit 20,000). Without a recipe app connection a notice at the top links to `/recipes/connect`.
- Server: `PlannerController` (stateless, the client sends offers/pantry back), `app/Ai/Assistant.php` (prompts + strict JSON schemas), `app/Ai/OpenAiClient.php` (Responses API via `Http`, no SDK; `OPENAI_MODEL` default gpt-6-luna (cheapest model that read the test offers reliably), `OPENAI_REASONING_EFFORT`). One global key for all users (free); keep the client per request so own user keys can be added later. Rate limit `throttle:ai` (60/h per user). Requests may take up to ~2 min (`set_time_limit`, `OPENAI_TIMEOUT`).
- Offers pool (`#/offers`, `resources/js/offers.js`, `OfferController`, `offers` table, server only, no offline sync): own offers plus the ones others shared (`shared`, default on; device setting `shoppinglist.share-offers` for read offers). Reading offers (`POST /planner/offers`, also used by the offers page) saves them in the pool and returns them with ids; the same offer (shop, name, brand, end date) is not added twice. Only the creator may edit or delete. Step 1 shows all offers of the pool by shop (collapsible, checkbox per offer, "All"/"None" per shop); a search above (`offerSearch`, device only, not synced; `offerMatches` in `helpers.js`: every word in name or brand, accent-insensitive, also used by `#/offers`) shows only the matching offers, opens their shops and "All"/"None" apply to the shown ones; only ticked ones are used, new ones of the pool start unticked, offers read in the planner are ticked. Expired or deleted offers drop out of the selection (`selectedOfferIds`, ids not in the pool are dropped on the next change). `DELETE /offers` with `store` deletes the own offers of a shop. Regional offers: shops whose offers differ by region are listed in `App\Support\ShopRegions` (only Migros, its ten cooperatives; Coop's offers are national; remove the Migros entry if the cooperatives merge as planned for 2027). Offers have `region` (null: everywhere; dropped if it does not belong to the shop); the AI reads it from the material, otherwise read offers get the user's region of the shop. Users pick a region per shop in the settings (`preferences.regions`, tag => key; `/me` `regions` lists them); `Offer::visibleTo` then hides shared offers of the shop's other regions. Without a chosen region all regions are shown (with a hint on `#/offers`). Planner steps use `<x-planner-step>` cards. `offers:prune` (daily) removes expired offers and undated ones after `Offer::UNDATED_DAYS`. Shared reading UI: `<x-offer-reader>` with `requests()` + `offerReader()`.
- Offers straight onto a list: a "+" at every offer in `#/offers` and in planner step 1 opens `offerToListDialog` (`app.js` `openOfferToList`/`addOfferTo`, no AI, works offline): pick a list (the last used first, `shoppinglist.offer-list`, device only) or a new one; the entry gets the offer name, the shop as tag and `offer.note` as note. If the product is already open there (`plannedMerges`), it asks: "Merge" (like the planner's merging) or "Add anyway". The note comes from the server: `Offer::note()` («Aktion −30 %, Bio Kartoffeln, CHF 3.95 (statt 5.60), bis 14.11.», product left out when it is the entry's name), sent as `note` by `Offer::toClient()` and used by `Assistant::shoppingList` for the planner's items. No link to the offer is stored on the item (no synced field). Tests: `OfferTest::test_offers_come_with_the_note_of_a_list_entry`.
- Seasons (`App\Support\Seasons`): suggestions prefer foods in season in Switzerland this month (fresh harvest, storage does not count). With a connected recipe app its season data (`/api/foods` `season_months`) ranks the candidates (offers, then pantry, then season), `season_month` is sent to its search and the seasonal names go to the AI (`seasonal`); without one (or without season data there) the copy `database/data/food-seasons.php` is used (source of truth: RecipeManager's file of the same name). Shown to the user: `/me` `season` (month + foods from the copy) marks seasonal products in the suggestions with a leaf (`seasonalFood`, same matching as `Seasons::among`), the planner links to the recipe app's season calendar (`<RECIPES_URL>/season`) and each suggestion names its seasonal foods (`uses_season`).
- Recipe suggestions are not saved. Saving is planning: "Plan" (`POST /planned-recipes`) saves one as planned recipe and removes it from the suggestions; step 3 and 4 list the planned recipes (`<x-planned-recipes>`, ✕ = unplan, `DELETE /planned-recipes/{id}/plan`; in step 3 it becomes a suggestion again). A new search replaces the suggestions and leaves out the planned ones (`withoutPlanned`, also excluded from the search); "Suggest more recipes" appends. Step 4 builds the list from the planned recipes; a second build (planned again before adding) only builds the ones not built yet (`unbuiltRecipes`, built ones are marked) and appends to the items. The recipes stay planned until the items are added to a list (new or existing, also merging): then `POST /planned-recipes/used` (`ids` = saved ids of `builtRecipes`, `added_at` = ms of adding; only own recipes, a retry gives the same result and does not unplan a recipe planned again later) sets `used_at` and `planned` false. The client queues it first (`shoppinglist.planned-used`, device only, removed with the local data), takes the recipes out of `planned` at once (`withoutUsed`) and sends the queue (`sendUsedRecipes`) right away, before loading the planned recipes (planner, Recipes tab), on foreground and when online again; cancelling ("Start over") keeps them planned. Cached old app versions do not send it, their recipes stay planned (✕ takes them out). Ingredients and shopping list entries use generic names ("Kartoffeln", not "Bio-Kartoffeln"); the offer stays linked (`offer`) and its product name goes into the item note when it differs (`Assistant::offerNote`).
- Shop codes: `Assistant::SHOPS` (the standard shops, keep in sync with the `stores` migration) → `items.stores`; offer details → `items.note`. Own shops are not passed to the AI.
- Recipe app ("white label"): `RECIPES_NAME` (quote values with spaces, e.g. `"Ammanns Best"`), `RECIPES_URL`, `RECIPES_CLIENT_ID`, `RECIPES_CLIENT_SECRET` (Passport client in the recipe app, redirect URI `<APP_URL>/recipes/callback`). OAuth flow in `RecipesConnectionController` (no input at all when the recipe app lists the client in `PASSPORT_TRUSTED_CLIENTS` and both use the same OIDC login; `sso=1` in the authorize URL only for users with `oidc_sub`, others get the recipe app's login form), API calls and token refresh in `app/Recipes/RecipesClient.php`, tokens encrypted in `users.recipes_connection` (`EncryptedArrayOrNull`: a value encrypted with another APP_KEY, e.g. after `ddev pull production`, reads as not connected). API contract: RecipeManager `AGENTS.md`. Locally the client lives in the RecipeManager DDEV database: after `ddev pull production` there it is gone (`invalid_client`); create a new one (`ddev artisan passport:client --name="Shoppinglist (lokal)" --redirect_uri=https://shoppinglist.ddev.site/recipes/callback -n`) and put ID and secret into `.env`.
- Recipes tab (`#/recipes`, `resources/js/recipe-history.js`, `PlannedRecipeController`, `planned_recipes`, server only): groups "Planned" (`planned` true: not on a list yet) and "On a list / earlier". Saved by "Plan" (`POST /planned-recipes`, `StorePlannedRecipeRequest`, sets `planned` and `planned_at` = date of the offers in `uses_offers`, shown as "Aktionen vom 6.11." in the dialog), when building the list (`POST /planner/list` sends the full planned recipes, `recipePayload`; saved without changing the plan, so the items' recipe links work), marked as on a list after adding the items (see above) and on import. "Plan again" (`POST /planned-recipes/{id}/plan` with the planner's `offer_ids` and selected pantry names from localStorage, `currentSelection`) sets `planned`/`planned_at` and recomputes `uses_offers`/`uses_pantry` by ingredient names (`App\Support\FoodNames`: main word of the ingredient vs. the words of the product, equal or start/end, no AI) and `uses_season` for the current month (recipe app season data, else the copy); own recipes without saved ingredients load them from the recipe app first. The planner and the tab tell each other by the `planned-recipe` window event. Existing entries were migrated as not planned (`planned_at` = last save). The limit only removes recipes that are not planned. `PlannedRecipe::remember`: own recipes once per recipe id (key `recipe-<id>`), AI ideas by key with ingredients and preparation, max. `PlannedRecipe::LIMIT` per user. Handing an idea to the recipe app (`POST /planner/recipes` with key and all details) saves it first if it is not saved yet (not planned) and sets `draft_url`. `POST /planner/list` returns `recipes: [{key, id}]` (recipe key → saved id, kept in `builtRecipes`, the items get it as `key`, `listRecipes`), maps the item recipe names back to the suggestion names and saves own recipes with the recipe app's ingredients. The tab caches the last loaded recipes (`shoppinglist.recipes`, removed with the local data) and shows per recipe the linked items from RxDB ("3/5 erledigt" in the row, items with list and status in the dialog, tap opens the list). `#/recipes/<id>` replaces itself with `#/recipes` and opens the dialog (back closes it, then leaves the tab): own recipe, else `GET /planned-recipes/{id}` (read only for members of a list with an item linked to it, `toShared` without `draft_url`; others 404), else a stand-in from the items (removed recipe).
- Own recipes in step 3 ("Add your own recipe", collapsible, device only): typing searches the recipe app by name (`POST /planner/recipe-search`, `throttle:60,1`, no AI, not behind `EnsureAiFeature`; proxies the recipe app's `POST /api/recipes/search` with `query`, which older recipe apps refuse with 422 → 502 with the usual message) and offers the found recipes with "Plan" (same payload as a suggestion of the recipe app, `source: recipes`). The typed name can always be planned as own dish (`source: custom`, key `custom-<uuid7>`, name and servings only, no ingredients): `POST /planned-recipes` saves it like an AI idea by its key; building the list sends it without ingredients and the AI adds the usual ingredients of the dish (`Assistant::shoppingList` prompt). Badges by source: `$recipeSource(source)` (`app.js`: AI idea, «Eigenes Gericht», recipe app name). Tests: `PlannerTest` (`test_own_recipes_are_found_by_name`, `test_a_typed_dish_is_planned_…`).
- Recipe details: `<x-recipe-dialog>` (Recipes tab and step 3; the component's `detail` + `$refs.recipeDialog`, actions in the slot). Navigating from a dialog uses `closeDialogThen` (`layers.js`), otherwise the pending back of the layer undoes the navigation.
- Adding the planner's items to an existing list asks first if some are already open there with the same unit, or with g/kg resp. ml/cl/dl/l (`plannedMerges`, `mergedAmount` converts into the open item's unit): merging adds the amounts and joins recipes, shops and notes.
- Unit conversion: the recipe app's `/api/recipes/{id}` returns `converted` per ingredient (g/kg or ml/dl/l, from its densities and piece weights). Before the AI builds the shopping list, `App\Recipes\RecipeIngredients::unify()` replaces the amount of a food used with different units across the chosen recipes (1 Tasse Mehl + 200 g Mehl) by its converted g/ml; foods with one unit keep it (2 Stk. Zwiebeln). Recipe apps without `converted` keep their units. AI ideas are not converted.
- Progress and errors are shown at the button that started a request (`run(key, label, action)`, `busyKey`/`errorKey`, `<x-spinner>`, `<x-planner-error>`). "Suggest more recipes" sends the shown ones as `exclude` (recipe ids + names) and appends the new ones unselected.
- Suggestions prefer recipes combining several offers: own recipes are searched by offer foods first, then pantry foods, and sorted by matched offers. With a connected recipe app, AI ideas use its categories, units and complexities (`GET /api/vocabulary`).
- AI ideas are never saved directly: "Import into …" posts them as a draft (`POST /api/recipe-drafts`, recipe import JSON) and opens the returned import wizard URL in a new tab, where the user matches foods, units and the category and picks cookbook and visibility. Unknown values can be omitted there, or requested (admins approve them).

## Rules

- Alpine proxies (e.g. arrays from `x-model` state) must be copied to plain values before `insert`/`incrementalPatch`: RxDB clones documents for the BroadcastChannel (DataCloneError).
- Every synced field must exist in the RxDB schema (`resources/js/db/schemas.js`), the resource document and the push validation (`SyncController`). Schema changes in RxDB need a schema version bump and migration strategy. Migration strategies keep values already present (`{ field: default, ...doc }`). If the server already fills the new field when the client updates, also bump the collection in `REPLICATION_RUNS` (`resources/js/db/index.js`): the old app version keeps syncing until the update is accepted, pulls the field without knowing it and moves its checkpoint past it; the new run pulls the collection again.
- Keep the app shell (`resources/views/app.blade.php`) free of user data, it is cached by the service worker.
